CCH Walkthrough

Phase 1 reads the graph's undirected skeleton, never a weight, and produces two things later phases reuse: an elimination order (which node goes at which rank) and the chordal supergraph (every arc, original or shortcut, a weight could ever be written into). Phase 2 then writes one set of weights into that structure: for every arc, the cheapest way between its ends through lower-ranked nodes only. Phase 3 answers shortest-path queries from the two. Below, each function runs on one small example. Every array and number on this page is real output from the PR's functions on that example.

How the functions connect

Topology::build (order.rs:183) is two calls: nd::nested_dissection_order produces rank_to_node, and Topology::from_order (order.rs:198) plays the elimination game in that order. The top lane works in node ids; once rank_to_node exists, everything works in ranks.

The example skeleton

A 3×3 grid whose node ids skip 3 and 7, the way a skeleton sized by node_cap carries unused id slots. The skeleton is a Csr (mod.rs:79): row_offsets holds node_count + 1 offsets, neighbors holds each row's node ids, sorted. Every edge appears twice, once in each endpoint's row. Rows 3 and 7 are empty.

nd.rs:46 · pub(super)

nested_dissection_order: check, set the isolated nodes aside, order the rest

fn nested_dissection_order(skeleton: &Csr) -> Result<Vec<NodeId>, OrderError>

Three checks first, in release builds too, each returning an error rather than panicking: no more than MAX_NODES nodes, offsets and ids in range (is_well_formed), and rows sorted, without repeats or self-loops, every entry mirrored (is_symmetric_simple).

Then one partition over the node ids splits them into nodes with an empty row and the rest. The empty-row list becomes the start of rank_to_node, so isolated ids take the lowest ranks. Only the connected nodes go to the backend, through order_connected_nodes. Its answer lists positions in connected, so each one is mapped back with connected[k] and appended. A wrong length or an out-of-range position is an OrderError::NotAPermutation.

nd.rs:91 · private

order_connected_nodes: copy into the backend's arrays and call it

fn order_connected_nodes(skeleton: &Csr, connected: &[NodeId]) -> Result<Vec<i64>, OrderError>

backend_id[node] gives each connected node its compact id, its position in connected. Isolated nodes are left at 0 and never read, because no connected row names them. Each connected row is then copied through backend_id into neighbors, with row_offsets holding the row starts. These are METIS's xadj and adjncy; the doc comment names them once. The backend reads signed 64-bit ids, which is why this is a copy and not a cast.

CscPattern::new re-checks offsets, ids and row order, and feral_metis::metis_order returns an order over compact ids. All three arrays are locals, freed when the function returns. A piece of at most 200 nodes (nd_to_amd_switch, feral-metis node_nd.rs:151) is not dissected: feral-metis orders it with approximate minimum degree (AMD). That is what happens to this 9-node grid: the four corners first, then the edge middles, the centre last.

What nested dissection does on a bigger graph

On a 32×32 grid (1,024 nodes, 1,984 edges) feral-metis does split. It finds a small set of nodes whose removal cuts the graph in two (a separator), gives the separator the highest ranks, and repeats inside each half until the pieces are 200 nodes or fewer. Placing each separator above everything it separates keeps shortcuts local.

Node-id order is row-major, the case the PR's nested_dissection_beats_node_id_order_on_a_grid test guards against. Dissection less than halves the arcs and cuts the elimination-tree height from 1,024 to 111, at the price of a higher worst-case row (separators become cliques).

The separators were read back from the ranks: the top k ranks of a piece count as its separator when removing them disconnects the piece. They add up to 110 nodes and 8 leaves (107, 124, 110, 119, 113, 113, 114, 114 nodes), the same counts feral-metis reports itself (n_separator_vertices = 110, n_amd_leaf_calls = 8).

order.rs:51–78 · pub(crate)

Rank: a position in the order, with its own type

#[repr(transparent)] pub(crate) struct Rank(NonZeroUsize); const fn new(index: usize) -> Self // stores index + 1 const fn index(self) -> usize // gives back index

A rank and a NodeId cannot be swapped by accident: node_of takes a Rank and rank_of takes a NodeId. Inside, a rank is stored as its index plus one in a NonZeroUsize. Zero is then never a valid value, so Rust uses it for None, and Option<Rank> takes 8 bytes, the same as Rank. Phase 2's middle-rank arrays rely on this: an arc with no middle stores None at no extra cost. Adding one keeps the order, so comparing two ranks compares their indices, and Debug prints the index.

order.rs:325 · private

invert: from "who goes at rank r" to "what rank is node u"

fn invert(rank_to_node: &[NodeId], node_count: usize) -> Result<Vec<Rank>, OrderError>

Called by from_order (order.rs:205), which does not trust the order it is given. It fills a Vec<Option<Rank>> that starts all None, writing node_to_rank[rank_to_node[r]] = r. A wrong length, a node the graph does not have, or a node listed twice (its slot is already set) is an OrderError::NotAPermutation, each with its own message. When every slot is set, the Options are unwrapped. Because Option<Rank> and Rank have the same layout, that collect reuses the same memory.

The elimination game, which chordal_supergraph computes in one pass

Take the nodes in rank order. When a node is eliminated, connect all of its remaining neighbours (the ones with higher rank) to each other. The edges this adds are fill arcs, the shortcuts. Original edges plus fill make the chordal supergraph. Nothing in the PR plays the game edge by edge: chordal_supergraph gets the same result by having each rank inherit its children's rows, and it builds the elimination tree as it goes. Here the game adds 5 fill arcs, 17 arcs in all; node-id order on the same skeleton gives 20.

order.rs:373 · private

chordal_supergraph: the upward rows, by inheriting from children

fn chordal_supergraph(skeleton: &Csr, rank_to_node: &[NodeId], node_to_rank: &[Rank]) -> RankRows

Builds up(r), the ranks above r that it is joined to, for r = 0, 1, 2, …, into one reused row buffer. First come r's own skeleton neighbours mapped to ranks, keeping those above r (order.rs:394–400). Then, for each tree child c, comes the finished row up(c) without r (order.rs:403–411). This is the game's rule restated: when c was eliminated, everything in up(c) was joined together, and r is the lowest of them, so r inherits the rest.

The buffer can now hold repeats (a rank two children share) and is out of order. sort_unstable followed by dedup fixes both (order.rs:415–416). The row is appended to the flat neighbors buffer, and its end goes into offsets. Children have lower ranks than their parent, so their rows are already final in that buffer when the parent reads them.

The elimination tree, read off each finished row

let mut first_child: Vec<Option<Rank>> = vec![None; node_count]; let mut next_sibling: Vec<Option<Rank>> = vec![None; node_count]; if let Some(&parent) = row.first() { next_sibling[index] = first_child[parent.index()].replace(rank); }

A rank's parent in the elimination tree is the lowest rank above it that it is joined to: the first entry of its sorted row. So as soon as row r is finished, its parent is known, and r is pushed onto the front of the parent's child list. The lists are two arrays. first_child[p] is the most recently added child of p, and next_sibling[c] is the child added before c. replace does both steps in one call: it returns the old first child and stores r in its place.

A parent always has a higher rank than its children, so by the time the loop reaches it, all of its children are listed. It then visits them newest first, which is why rank 7 reads child 6 before child 2.

order.rs:433 · private

transpose: the downward rows

fn transpose(upward: &RankRows) -> RankRows

Row r of downward lists the lower ranks whose upward row contains r. It is a counting sort: count the entries for each target, turn the counts into offsets with a running total, then go through the upward rows in increasing order, so each downward row comes out ascending. The Topology doc says only an incremental recustomization needs it.

Phase 2: customization

Phase 2 is the only phase that reads a weight, and the only one that runs again when weights change. It takes Phase 1's Topology as it is and fills in a metric. For every arc slot, in each direction, it stores the cheapest way between the arc's two ends that passes only through lower-ranked nodes, and the node that way goes through. The example is the same 3×3 grid, now with weights.

How Phase 2 connects

Cch::build (customize.rs:324) first checks that the skeleton and the weights are both for the input's node count. It then runs Phase 1 on the skeleton, wraps the result in an Arc, and runs customize on the weights. Cch::customized (customize.rs:352) runs the same customize against the Topology an existing hierarchy holds, and returns a new Cch that shares it. customize has three steps: check the weights, write the original edges into their slots, then improve every slot through lower-ranked detours.

What Phase 2 computes

Four arrays, each with one value per arc slot, so each is as long as upward.neighbors (17 here). Slot k is the arc between ranks lower and higher:

arraytypeslot k holds
upward_weightBox<[f64]>the cheapest lower → higher path whose stops in between all rank below lower; ∞ if there is none
downward_weightBox<[f64]>the same for higher → lower
upward_middleBox<[Option<Rank>]>the rank that path goes through, or None when it is the original edge itself
downward_middleBox<[Option<Rank>]>the same for downward_weight

On this page ∞ is f64::INFINITY, and a dash in a middle array is None. Amber cells are fill slots, as on the Phase 1 strips.

The example weights

CchInput.weights is a WeightCsr (mod.rs:159): a Csr plus values, one weight per entry. It is directed: row u lists v for every edge u → v, so a two-way road is two entries. The roads are:

  • ring roads cost 1;
  • roads into the centre cost 4;
  • the road 9–5 is slow (7);
  • the road 1–5 is closed in both directions (+inf);
  • 2 → 6 is one-way, so row 6 has no entry for 2.

That makes 23 entries.

customize.rs:136 · private

validate: refuse weights the hierarchy cannot use

fn validate(topology: &Topology, weights: &WeightCsr) -> Result<(), CchError>

Runs before anything is written, as three checks in order, each before anything reads what it guards:

  1. Node count. If the weights are for a different number of nodes than the topology, they come from a later version of the graph, which has since gained nodes. That returns CchError::NeedsRebuild. On a live graph this is expected, not a bug.
  2. Shape. The CSR must be well formed (Csr::is_well_formed: node_count + 1 offsets from 0, never decreasing, ending at the number of entries, and every neighbor below node_count), with one weight per entry and every row strictly ascending. CchInput::build always produces that shape, so a miss is a bug: Internal("the weight CSR is malformed").
  3. Values. A NaN or a weight below zero (−∞ included) returns CchError::InvalidWeight. -0.0 < 0.0 is false, so −0.0 passes and behaves as 0. +∞ passes: it means a closed road, which seed treats exactly like a missing one.

The other "later graph" case, an edge between two nodes that have no arc, can only be found while seeding, after the value check. Weights with both a new edge and a NaN therefore return InvalidWeight, which a rebuild would refuse the same way.

customize.rs:204 · private

seed: write each original edge into its slot

fn seed(topology: &Topology, weights: &WeightCsr) -> Result<Metric, CchError>

Starts with ∞ in both weight arrays and None in both middle arrays. Then it makes one pass over the entries; WeightCsr::entries (customize.rs:168) yields (u, v, weight) row by row.

  • A self-loop is skipped.
  • Otherwise both nodes become ranks with rank_of. arc_slot(rank_u, rank_v) takes the two ends in either order and finds the slot with a binary search in the lower end's row.
  • If u has the lower rank, the edge runs upward and its weight goes into upward_weight; otherwise into downward_weight.
  • If there is no slot, the graph has gained an adjacency since the hierarchy was built: NeedsRebuild.

The doc comment notes that C works the other way round: for every arc it looks up both W(u, v) and W(v, u), two lookups that miss on every fill arc.

customize.rs:264 · private

relax: improve every arc through lower detours, in one pass

fn relax(topology: &Topology, metric: &mut Metric)

Takes the ranks x = 0, 1, 2, … in order. For every pair y < z in up(x), the three ranks form a triangle with x at the bottom. Two detours are tried for the top arc y–z:

  • y → x → z for its upward weight: downward_weight of x–y plus upward_weight of x–z;
  • z → x → y for its downward weight.

A sum is written only if it is strictly smaller, and then x is recorded as the middle.

Finding the top arc without a search. Eliminating x joined every pair in up(x), so every z above y in up(x) is also in up(y). Both rows are ascending. So for each y, a cursor starts at the front of up(y) and only moves forward as z moves forward: each z is found where the previous search stopped. On this example the 11 triangles take 15 comparisons in all.

x = 6
x, being processed up(x) top arc improved top arc checked, kept slot written at this step

Why one pass is enough

The module doc (customize.rs:77–85) gives the argument. When x is processed, the arcs x–y and x–z are already final. A detour that could shorten them would pass through a rank below x, and every such rank was processed earlier. The top arc y–z always exists, because Phase 1 joined every pair in up(x). So nothing has to be repeated until the values stop changing.

Ties

Every improvement is a strict <, so a tie never moves an arc. The module doc (customize.rs:66–75) states the two rules this gives:

  • An original edge that a detour only ties keeps its own weight, and gets no middle. The PR's test: 1–2 weighs 2 directly, and also 2 through apex 0.
  • Among detours that tie, the lowest apex is the middle, because it is reached first. In this example, slot 16 shows it at x = 8.

Together they make the result one exact set of arrays for a given order and metric. A later scoped or parallel version can be compared with it bit for bit. The tests check both rules on every slot of the test kit's graphs.

The finished metric

The arrays after relax. Highlighted slots changed during relax. Three slots show what the rules do:

  • Slot 11 (ranks 7–8, nodes 1–6) is a fill arc whose only route uses the one-way road. 1 → 2 → 6 costs 2, and there is no way back below rank 7, so downward_weight stays ∞.
  • Slot 13 (ranks 7–10, nodes 1–5) is the closed road. The arc is still there, and relax gives it 6 through rank 6 (node 4), the detour 1 → 0 → 4 → 5.
  • Slot 16 (ranks 9–10, nodes 9–5) starts at 7. At x = 6 the detour through node 4 costs 6 and wins. At x = 8 the detour through node 6 also costs 6. That is not smaller, so the middle stays 6.

What a middle is for

A middle says how to expand an arc into real roads, which is what Phase 3 does to report a path. An upward arc lower → higher with middle m is the arc m–lower taken downward, then m–higher taken upward. A downward arc is the mirror image. Expanding stops at slots with no middle, which are original edges.

Phase 3: query

Phase 3 answers "what is the cheapest path from node s to node t?" using only the hierarchy. It runs two small searches that only ever move to higher ranks, one from each end, takes the cheapest rank both reached, and then expands the shortcut arcs on that route back into real roads. How a query runs

Cch::query (mod.rs:269) hands straight to query (query.rs:237). Everything between the two id conversions happens in rank space. The function keeps no state between calls, so many queries can run at once against one hierarchy.

Why searching upward from both ends is enough

Take any shortest path and look at the ranks of the nodes along it. It goes up and down, and somewhere it reaches its highest rank. Every stretch where it dips below both ends of that stretch is exactly what Phase 2 stored in one arc: the cheapest way between two nodes through lower-ranked nodes only. Replace each dip by its arc and what is left only climbs from s to the peak, and only climbs from t to the peak.

So a search from s that follows only upward arcs, and one from t that follows only upward arcs backwards, both reach the peak with the right distance. The module doc (query.rs:9–13) states this.

search: Dijkstra over the upward arcs only

fn search(cch: &Cch, start: u64, direction: Direction) -> FxHashMap<u64, Reached> struct Reached { dist: f64, pred: Option<u64>, finalized: bool } // query.rs:29 struct Candidate { dist: f64, rank: u64 } // query.rs:40

Ordinary Dijkstra with a heap, except that from a rank it only looks at up(rank). Direction::Forward reads up_w (travelling lo → hi); Direction::Backward reads dn_w, which is the same climb done against the direction of travel, so it finds distances to the target. An arc whose weight is ∞ in that direction is skipped (query.rs:122) and never enters the map.

BinaryHeap pops the largest item, so Candidate's ordering is reversed (query.rs:47): the nearest pops first, and on equal distance the lowest rank. A rank can sit in the heap more than once; when it is popped a second time, finalized is already set and the entry is skipped. The search runs until the heap is empty and returns every rank it reached, with its distance and the rank it came from.

Meeting: the cheapest rank both searches reached

Walks the smaller of the two maps and, for every rank also in the other map, adds the two distances. The smallest sum wins. On an equal sum the lower rank wins, because the map's order is not fixed and the same query must always return the same path.

Data layout: four arrays, or one array of structs

Every per-arc value lives at one arc slot, in one of four arrays: upward_weight, downward_weight, upward_middle, downward_middle. That is a struct of arrays (SoA). The other way to store it is an array of structs (AoS): one 32-byte record per arc that holds all four. This part follows which fields each phase reads and writes, in what order, and what that means for each layout, including an AoS stored in a GraphBLAS matrix with a user-defined type.

Sources: git show origin/main: and git show fxr/12a: of the files under graph/src/index/falkordb/cch/. Phase 3 on origin/main no longer runs the heap-based search shown above. It walks each endpoint's elimination-tree ancestor chain (Chain::relax_from, query.rs:99). Both versions read the same arrays per relaxed arc, so the analysis below holds for either. Byte counts come from the types in the code. Figures marked measured come from the benchmark in Benchmark results at the end of this part. That benchmark compared flat SoA, chunked SoA and an AoS stored as a GraphBLAS UDT. A plain Rust AoS was not benchmarked, so statements about it, and cache-line counts in general, stay inferred.

What a query touches

Climbing. For each rank on its chain, a half reads two offsets (up_range), then walks that rank's row: one neighbour and one weight per arc. The forward half reads only upward_weight and the backward half only downward_weight. No middle is read while climbing. Inside a row both reads are sequential, because the row's slots are consecutive. Between rows they jump: the next rank on the chain is an ancestor in the elimination tree, and its row can sit anywhere in the arrays.

Unpacking. For each arc popped off the stack, arc calls arc_slot: two offsets and a binary search in the lower end's row of upward.neighbors. Then it reads the weight and middle of that one direction. unpack uses only the middle. The two halves of an expanded arc are rows of lower ranks, so unpacking is a random access per arc, with no sequential run to exploit.

While climbing, AoS brings the other direction's weight and both middles along with every record: about 2.5 times the bytes per relaxed arc. The benchmark shows what limits the climb. On flat SoA it is instruction-bound, not miss-bound (measured: 94% of samples in relax_from, IPC 4.4, 1.34M instructions per query). The search relaxes every upward arc of every ancestor on both chains, so the arithmetic dominates, not the jumps. Distance-only queries took 71 µs on flat SoA and 76 µs on chunked SoA, where each weight read pays one extra dependent load through the chunk table (measured).

The GraphBLAS AoS took 162 µs per query, 2.3 times flat (measured). Its IPC was the same (4.3), but it ran 3.0M instructions per query, and 30% of samples (plus 4.5% in the stub) were in memmove. GxB_Iterator_get_UDT copies the whole 32-byte entry when the search needs 8 bytes. That copy is specific to the GraphBLAS API. How much of the extra bytes alone would cost a plain Rust AoS, which reads in place, was not measured (inferred: less than the UDT, because the climb is not miss-bound).

Unpacking is cache-miss bound on SoA (measured: 66% in arc_slot's binary search, IPC 1.6; 137 ms for 10,000 routes, 3.98M hops). The GraphBLAS AoS took 181 ms, only 1.32 times flat: its extractElement_UDT costs 238 instructions against arc_slot's 94, but the miss on the row hides most of the difference (measured).

Vector instructions are not a deciding factor. The climb's inner loop is dist + weight and a compare per arc, over a handful of arcs per row, with a gallop through the chain between rows. SoA would let the compiler vectorize that loop, but a handful of arcs gives it little to work with (inferred).

What customization touches

Full sweep. relax runs x over the ranks in increasing order. It does not read the downward rows: every triangle is found from the upward side. For each pair y < z in up(x), it reads the two bottom arcs (x, y) and (x, z), both directions each, then updates the top arc (y, z), whose slot it finds by stepping a cursor along up(y).

  • The bottom arcs are slots in x's own row. Both weights are read, never the middles. The run is sequential and stays in cache for the whole of x's pairs.
  • The top arc is in y's row, which can be anywhere. Both weights are read, compared and written back on a strict improvement, and the middle of each improved direction is written. As z climbs, the slot moves forward inside y's row, so the scatter is one random jump per y, followed by a short forward run.

So the fields that are used together are exactly the four fields of one arc: the two weights are always read together, and a middle is written only next to its weight. The fxr/12a doc comment on Buffers (customize.rs:282–289) says the sweep "is bound by the latency of its scattered reads". The benchmark agrees (measured): on flat SoA, full customization of California's 53.9M triangles took 291 ms, 80% in the relax sweep and 20% in the seed's arc_slot binary search per edge. That is about 50 instructions per triangle at IPC 2.7, a tight loop whose cost is the scattered loads of rows y and their weight slots. Of the 53.9M triangles, 9.08M improve their top arc.

Scoped recustomization (partial.rs, fxr/11 and later) works the other way round. It pops arcs (lo, hi) in increasing lo from a heap, and finds each arc's lower triangles by merging the downward rows down(lo) and down(hi). For each common x it calls arc_slot twice (two binary searches in up(x)), reads both weights at both slots, and then writes all four fields of (lo, hi). Every one of those reads is a random slot.

Where AoS could help. The random accesses in customization use both directions of one arc together, and sometimes the middles too. A 32-byte record aligned to 32 bytes never straddles a 64-byte line, so the top-arc update becomes one miss instead of two to four. For a sweep bound by miss latency, that is the one place a plain Rust record layout should pay off. This is inferred: the benchmark's AoS went through GraphBLAS calls, whose overhead swamps any line-count gain, so it does not test it. A middle ground keeps that possible gain without the query cost: pair only the two weights as a 16-byte record and keep the middles in their own arrays. The climb would then use 8 of 16 bytes instead of 8 of 32, and only unpacking and the improving writes would touch the middles.

Where AoS hurts. The sequential bottom-arc reads carry the middles along for nothing. Seeding fills four arrays with ∞/None and then writes one weight per edge, which is the same in both layouts. The query, which runs far more often than customization, reads one field in four (above).

What a new version costs

On origin/main the four arrays are Box<[T]> with no new_version. A new version means a whole new Metric: 32 bytes per arc, 187 MB on California, written in full for any change.

On fxr/12a each array is a WeightArr: chunks of 2,048 slots, each behind its own Arc, with the chunk table behind an Arc too. new_version is one Arc bump per array. The first set on a version clones the table (one Arc bump per chunk), and the first write to a chunk copies that chunk only: 16 KB of one array. A read costs one extra dependent load through the table.

All four tiles are measured (benchmark below). Writing one arc's four fields on chunked SoA owns 248,128 B: four chunk tables of 2,851 Arcs and four 2,048-slot chunks. That is about 35 times faster than the flat clone and owns about 750 times fewer bytes. The +54 ms on full customization is the final cut of the flat Buffers into chunks, one extra copy of 187 MB, which the doc comment chose because chunked reads are about a quarter slower inside the sweep. A chunked AoS would copy 2,048 records (64 KB) per touched chunk, the same bytes per slot range as the four SoA chunks together (inferred). Scoped recustomization writes all four fields of each arc it changes, so it touches the same four SoA chunks either way.

The array of structs as a GraphBLAS matrix

The tempting version of AoS is a GrB_Matrix over ranks with a 32-byte user-defined type (GrB_Type_new), one entry per arc at (lower, higher). Held by row, its row pointers and column indices are the upward CSR, and its values array is the AoS. The Rust side already declares the calls it would use (graph/src/graph/graphblas/mod.rs): GrB_Matrix_extractElement_UDT, GrB_Matrix_setElement_UDT, GxB_rowIterator_seekRow, GxB_rowIterator_nextCol, GxB_Iterator_get_UDT. Each one is an extern "C" function. The C header's inline macro forms cannot be used from Rust.

With extractElement reading the top arc, GB_Matrix_find_entry alone is 39%, extractElement_UDT 13% and the OpenMP flush about 4%.

Copy-on-write in GraphBLAS works per array: the row pointers, the indices and the values are each shared or owned as a whole. Getting chunk-sized sharing on top of a GrB matrix would mean splitting the hierarchy over many matrices (one per block of rows, with a table of them) or adding chunked value arrays inside GraphBLAS. Either way the data structure gets more complicated and the code gets slower, because every access first has to find the right matrix or chunk and then still pays the call and the lookup.

The way out that GraphBLAS offers is to unload the arrays (GxB_Matrix_unload or a GxB_Container) and work on the raw buffers in Rust. At that point the matrix is only a container: the code is back to plain arrays, and the per-array copy-on-write still applies when the buffers are loaded back in. The benchmark did not test this variant. A bulk formulation of the sweep (for example, masked min-plus products level by level over the elimination tree) would avoid the per-entry calls. The tie rules and the rank order the sweep depends on make that an open design question, and this page does not answer it.
